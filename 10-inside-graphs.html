Inside Graphs

A tree is a graph that promised not to have cycles. Drop that promise and you get the structure behind maps, dependencies, social networks and build systems — plus one new obligation: remember where you've been.

Anatomy of a graph

Vertices joined by edges. That's the whole definition — every distinction below is about what the edges are allowed to do.

Representations

The same graph, stored three ways. The choice is decided by one question: is your graph sparse or dense?

Your vertex type is a Map key

Everything from Inside Java Maps applies: the vertex needs a correct equals/hashCode pair, and it must be immutable. Mutate a vertex after inserting it and the graph loses track of it — present in size(), unreachable by lookup. A record is the natural choice.

BFS and DFS

Same algorithm, different container. Swap the queue for a stack and breadth-first becomes depth-first — and the visited set is what stops a cycle from looping forever. 

// BFS — shortest path by edge count on an unweighted graph
Deque<String> queue = new ArrayDeque<>();
Set<String> seen = new HashSet<>();

queue.add(start);
seen.add(start);                       // ← mark on ENQUEUE, not on dequeue

while (!queue.isEmpty()) {
    String node = queue.poll();
    visit(node);
    for (String next : g.getOrDefault(node, List.of())) {
        if (seen.add(next)) queue.add(next);    // add() returns false if present
    }
}

// DFS — same code, one word different
Deque<String> stack = new ArrayDeque<>();
stack.push(start);
while (!stack.isEmpty()) {
    String node = stack.pop();
    if (!seen.add(node)) continue;
    visit(node);
    for (String next : g.getOrDefault(node, List.of())) stack.push(next);
}
Mark visited when you enqueue, not when you dequeue

If you only mark on dequeue, a vertex reachable from several others gets pushed once per incoming edge. On a dense graph that turns a linear walk into an exponential one — the traversal still terminates and still gives the right answer, so it looks correct right up until the graph gets big.

Detecting cycles

The test is different for directed and undirected graphs, and using the wrong one gives confident wrong answers. 

// UNDIRECTED — "visited, and not the node I came from"
boolean hasCycle(String node, String parent, Set<String> seen) {
    seen.add(node);
    for (String next : g.get(node)) {
        if (next.equals(parent)) continue;          // the edge we arrived on
        if (seen.contains(next)) return true;
        if (hasCycle(next, node, seen)) return true;
    }
    return false;
}

// DIRECTED — three colours. "Visited" is not enough.
//   WHITE = untouched   GREY = on the current path   BLACK = fully explored
boolean hasCycle(String node, Map<String, Colour> c) {
    c.put(node, Colour.GREY);
    for (String next : g.getOrDefault(node, List.of())) {
        Colour n = c.getOrDefault(next, Colour.WHITE);
        if (n == Colour.GREY) return true;            // a back edge — a real cycle
        if (n == Colour.WHITE && hasCycle(next, c)) return true;
    }
    c.put(node, Colour.BLACK);                       // off the path now
    return false;
}

In a directed graph, reaching an already-visited vertex is not a cycle — a diamond A→B→D, A→C→D visits D twice with no cycle anywhere. Only reaching a vertex that is still on the current path proves one. That's what grey means.

Connected components

A graph need not be one piece. Counting the pieces is a loop around your traversal. 

int components = 0;
Set<String> seen = new HashSet<>();

for (String v : g.keySet()) {
    if (seen.contains(v)) continue;
    bfsFrom(v, seen);        // marks everything reachable
    components++;            // one new island
}

For directed graphs the equivalent is a strongly connected component — a group where every vertex can reach every other. Kosaraju's algorithm finds them with two passes of DFS (the second on the reversed graph); Tarjan's does it in one pass using low-link numbers. Both are O(V+E), and both are worth reaching for a library rather than writing from memory.

Dijkstra

Shortest path when edges have weights. BFS always expands the nearest hop; Dijkstra always expands the cheapest known total. 

record Step(String node, int dist) { }

Map<String, Integer> best = new HashMap<>();
PriorityQueue<Step> pq =
    new PriorityQueue<>(Comparator.comparingInt(Step::dist));

best.put(start, 0);
pq.add(new Step(start, 0));

while (!pq.isEmpty()) {
    Step cur = pq.poll();

    // PriorityQueue has no decrease-key, so we push duplicates and
    // skip the stale ones here. This is the standard Java idiom.
    if (cur.dist() > best.getOrDefault(cur.node(), Integer.MAX_VALUE)) continue;

    for (Edge e : weighted.getOrDefault(cur.node(), List.of())) {
        int alt = cur.dist() + e.weight();
        if (alt < best.getOrDefault(e.to(), Integer.MAX_VALUE)) {
            best.put(e.to(), alt);
            pq.add(new Step(e.to(), alt));      // may be a duplicate — fine
        }
    }
}
Why the "stale entry" line exists

Textbook Dijkstra calls decrease-key to reprioritise a vertex already in the heap. PriorityQueue has no such operation — remove(Object) is O(n). So the idiom is to push a second entry with the better distance and discard the outdated one when it surfaces. Leave that guard out and the algorithm still works, but it re-expands settled vertices and quietly loses its complexity guarantee.

When Dijkstra fails

One negative edge and it returns a wrong answer — with no error and no warning.

Dijkstra settles a vertex the moment it pops it, on the reasoning that no later path could be cheaper. A negative edge breaks exactly that reasoning: a longer route can become cheaper further along, after the vertex is already final.

Algorithm Handles Cost Use when
BFS Unweighted O(V + E) All edges cost the same
Dijkstra Non-negative weights O((V + E) log V) The normal case
Bellman-Ford Negative weights O(V · E) Negative edges exist; also detects negative cycles
A* Non-negative + a heuristic ≤ Dijkstra You can estimate the remaining distance
Floyd-Warshall All pairs O(V³) Small graph, every pair needed

A* is Dijkstra ordered by distance + estimate-to-goal instead of distance alone. The estimate must never overestimate — an admissible heuristic — or you lose the guarantee of finding the shortest path. Straight-line distance is the classic admissible heuristic for map routing, because no road is ever shorter than the crow's flight.

Topological sort

Order the vertices of a DAG so every edge points forward. This is what a build tool, a task scheduler and a module loader all run. 

Map<String, Integer> inDegree = new HashMap<>();
g.keySet().forEach(v -> inDegree.putIfAbsent(v, 0));
g.values().stream().flatMap(List::stream)
 .forEach(v -> inDegree.merge(v, 1, Integer::sum));

Deque<String> ready = inDegree.entrySet().stream()
    .filter(e -> e.getValue() == 0).map(Map.Entry::getKey)
    .collect(Collectors.toCollection(ArrayDeque::new));

List<String> order = new ArrayList<>();
while (!ready.isEmpty()) {
    String v = ready.poll();
    order.add(v);
    for (String next : g.getOrDefault(v, List.of())) {
        if (inDegree.merge(next, -1, Integer::sum) == 0) ready.add(next);
    }
}

if (order.size() != inDegree.size())
    throw new IllegalStateException("cycle detected");

Union-Find

Not a graph traversal at all — a structure that answers "are these two in the same group?" in effectively constant time. It's the engine behind Kruskal's algorithm. 

class UnionFind {
    private final int[] parent, size;

    UnionFind(int n) {
        parent = IntStream.range(0, n).toArray();   // each its own root
        size   = new int[n]; Arrays.fill(size, 1);
    }

    int find(int x) {
        if (parent[x] != x) parent[x] = find(parent[x]);   // path compression
        return parent[x];
    }

    boolean union(int a, int b) {
        int ra = find(a), rb = find(b);
        if (ra == rb) return false;                     // already together
        if (size[ra] < size[rb]) { int t = ra; ra = rb; rb = t; }
        parent[rb] = ra;                                // union by size
        size[ra] += size[rb];
        return true;
    }
}

Minimum spanning tree

The cheapest set of edges that keeps every vertex connected. Two algorithms, both greedy, both correct.

Kruskal Prim
Greedy on Globally cheapest edge Cheapest edge leaving the built tree
Needs Union-Find + sorted edges A PriorityQueue
Cost O(E log E) O(E log V)
Suits Sparse graphs, edge lists Dense graphs, adjacency lists 
// Kruskal — sort every edge, take it unless it closes a cycle
edges.sort(Comparator.comparingInt(Edge::weight));
UnionFind uf = new UnionFind(vertexCount);
List<Edge> mst = new ArrayList<>();

for (Edge e : edges) {
    if (uf.union(e.from(), e.to())) mst.add(e);   // false ⇒ would form a cycle
    if (mst.size() == vertexCount - 1) break;       // a spanning tree, by definition
}

That V − 1 is not a coincidence: a spanning tree of V vertices always has exactly V−1 edges, which is the same fact from Inside Trees read backwards.

Ways to get hurt

Forgetting the visited set

The one difference between tree code and graph code. A tree has no cycles, so tree traversal needs no memory of where it's been; a graph does, and without it the first cycle loops forever. If you adapted tree code and it hangs, this is why.

Marking visited on dequeue

Discussed above and worth repeating, because the symptom is performance rather than wrongness: the answer stays correct while the work becomes exponential, so it passes every small test and dies on real data.

Running Dijkstra on negative edges

No exception, no warning — just a wrong shortest path. If weights can be negative (refunds, elevation changes, penalties), you need Bellman-Ford. Worth an explicit guard if the weights come from outside your code.

Adding an undirected edge once

// ✗ half an edge — B never knows about A
g.computeIfAbsent(a, k -> new ArrayList<>()).add(b);

// ✓ both directions
g.computeIfAbsent(b, k -> new ArrayList<>()).add(a);

Traversals from A still find B, so it looks fine until something starts at B.

Recursive DFS on a large graph

Recursion depth follows the longest path. A chain of a million vertices overflows the stack, and StackOverflowError isn't something you can usefully recover from. Use an explicit Deque when the graph's shape isn't yours to guarantee.

Mutable vertices

Your vertex is a HashMap key. Change a field that hashCode() reads and it becomes unreachable — the same failure as in Inside Java Maps, reached by a different road. Use records.

An adjacency matrix for a sparse graph

A hundred thousand vertices with a handful of edges each needs 1010 matrix cells — tens of gigabytes to store almost entirely zeros. The matrix only pays for itself when the graph is genuinely dense or very small.

The short version

Model it as Map<V, List<V>>, keep vertices immutable, and never traverse without a visited set. BFS for fewest hops, Dijkstra for cheapest with non-negative weights, topological sort for ordering, Union-Find for connectivity. Reach for JGraphT the moment the algorithm has a person's name you'd have to look up.
