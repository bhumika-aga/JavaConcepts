Zero to a Million Users

Nobody designs the million-user architecture on day one — they arrive at it, one bottleneck at a time. This is that sequence: what breaks, in what order, and what you add in response.

What "a million" means

Before anything else: a million users is not a million requests. Conflating the two is how people over-build for traffic that never arrives.

Number Means Typical ratio
Registered users Everyone who ever signed up The vanity number
Daily active (DAU) Who shows up today Often 10–20% of registered
Concurrent users Active right now Often 1–10% of DAU
Requests per second What the servers actually feel The only one that sizes hardware 
// 1,000,000 registered → maybe 200,000 DAU
// 200,000 DAU × 30 requests each  = 6,000,000 requests/day
// 6,000,000 / 86,400 s            ≈ 70 requests/second average
// peak ≈ 2–3× average             ≈ 150–200 requests/second

Two hundred requests per second is not a hard problem. A single well-tuned server can serve that. Most systems described as "at scale" are handling a few hundred requests per second against a few hundred gigabytes of data — and the complexity in them is usually about availability and team size, not raw load.

The only real rule

Add a stage when you have measured the bottleneck it solves. Not before.

Every step below costs something permanent: more moving parts, more failure modes, more to operate at 3am. Each one is worth it at the point the previous design stops coping and is dead weight before then. The sequence matters as much as the contents — adding sharding before caching, for instance, is a great deal of work to solve a problem caching would have made disappear.

Premature scaling is the more common failure

Far more projects die from complexity they didn't need than from traffic they couldn't handle. A single server with a well-indexed database will take a real product further than most engineers expect — and the version of you that has actual traffic will make far better decisions than the version guessing today.

Stage 0 · One box

Web server and database on the same machine. This is the correct architecture for a new product, and it is not embarrassing.

Before changing the architecture, exhaust the cheap fixes: add the missing index, fix the N+1 query, turn on connection pooling, raise the instance size. Vertical scaling is underrated — cloud machines now reach hundreds of cores and terabytes of RAM, and a bigger box requires no new failure modes. It has a ceiling and it's a single point of failure, but it buys time at almost no complexity cost.

Stage 1 · Split the database off

Move the database to its own machine. The first structural change, and the one with the best ratio of benefit to regret.

Now each can be sized for what it actually does — the database gets memory and fast disks, the app gets CPU — and they stop stealing resources from one another. It also means the app tier can be replaced or restarted without touching the data, which is the precondition for everything that follows.

The cost is one network hop on every query, which is why connection pooling stops being optional: opening a TCP connection and authenticating per query will dominate your latency. Set the pool size deliberately — a pool far larger than the database's worker count just moves the queue somewhere less visible.

Also do this now

Take backups and verify a restore. A backup you have never restored is a hypothesis, not a backup. This is the cheapest it will ever be to test, because the dataset is still small.

Stage 2 · Load balancer and a second app server

One app server is a single point of failure and a hard ceiling. Two behind a load balancer fixes both — provided the servers hold no state.

Session data in an app server's memory is the usual violator: a user logs in on app 1, their next request lands on app 2, and they're logged out. Three ways out, in increasing order of preference:

  • Sticky sessions — the balancer pins a user to one server. Works, but wrecks even distribution and loses the session when that server dies. A stopgap.
  • Shared session store — sessions in Redis. Servers stay interchangeable, at the cost of one network read per request.
  • Tokens — put signed claims in a JWT or cookie, so there's no server-side session at all. The cleanest, with the caveat that revoking a token before it expires needs its own mechanism.

The load balancer also becomes your health-check enforcement point: an instance that fails its check stops receiving traffic automatically, which turns most single-instance failures into a non-event.

Stage 3 · Database replication

Most applications read far more than they write. Replicas let reads scale sideways — and introduce the first place where your data can be visibly out of date.

Replication also gives you failover — promote a replica when the primary dies — and a place to run expensive analytical queries without touching the machine serving customers. What it does not give you is write scaling: every write still goes through one primary. That ceiling is what eventually forces sharding.

Stage 4 · Cache

The highest-leverage change on this list. A cache in front of the database routinely removes 80–95% of read traffic for the cost of one Redis instance.

The pattern is cache-aside: look in the cache, and on a miss read the database and store the result with a TTL. On a write, update the database and delete the key rather than updating it — two concurrent writers updating a cache can finish out of order and leave a stale value there permanently, whereas a delete forces the next read to fetch fresh.

Good cache candidate Poor candidate
Read often, written rarely Written as often as read
Expensive to compute A trivial indexed lookup
Tolerates being seconds stale Must be exact — balances, stock counts
Shared across many users Unique per user and used once
Caching is where correctness bugs come from

Every cached value is a copy that can disagree with the truth. Before caching anything, answer "how stale may this be?" — and if nobody can answer, it isn't ready to cache. Watch for the thundering herd too: a hot key expiring sends every concurrent request to the database at once. Jitter your TTLs so keys don't expire in lockstep.

Stage 5 · CDN and static content

Images, scripts, stylesheets and video are usually most of your bytes and none of your logic. Serving them from your app servers is waste.

A CDN copies static files to edge locations near users, so a request from Singapore is answered from Singapore rather than crossing an ocean twice. That removes both the bandwidth and the round-trip — and a cross-continent round trip is on the order of 150ms, which no amount of backend tuning recovers.

The operational cost is invalidation. A file cached at the edge with a long TTL stays cached even after you deploy a new version. The standard answer is content hashing in the filename — app.9f2c1b.js — so a new build produces a new URL and the old one simply stops being requested. Never cache HTML the way you cache assets; the HTML is what points at the hashed filenames.

Stage 6 · Queues and workers

Some work doesn't need to finish before the user gets a response. Moving it off the request path shortens latency and stops slow jobs from consuming web threads.

Queue depth is the metric to alarm on: rising depth means consumers aren't keeping up, and it tells you well before users notice. The trade is that work is now eventually done, so the interface has to reflect that — "we'll email you when the export is ready" rather than a spinner. Messaging in depth is in Inside Kafka.

Stage 7 · Sharding the database

The last resort, and the one that's genuinely hard to undo. You reach it when a single primary can no longer absorb the writes, or the data no longer fits one machine.

Before sharding, make sure you've genuinely exhausted the alternatives: a bigger primary, moving cold data to archive tables, moving high-volume non-relational data (logs, events, sessions) out to a store built for it, and caching harder. Each of those is reversible. Sharding is not.

Pick the key from your access patterns: shard by the thing that appears in the WHERE clause of your hottest queries, so a typical request touches exactly one shard. Hash-based keys distribute evenly but destroy range queries; range-based keys keep ranges fast but create hotspots as data grows. The same power-of-two rehashing idea from Inside Java Maps scales up here as consistent hashing.

Stage 8 · Multiple regions

Two reasons to go multi-region, and they demand different designs: getting closer to users, and surviving the loss of a whole datacentre.

Routing is the easy half — geo-aware DNS or anycast sends each user to the nearest healthy region. The hard half is data. Replicating a database across regions means accepting either write latency measured in hundreds of milliseconds (synchronous) or genuine divergence between regions (asynchronous). There is no third option; this is the CAP trade from Inside Microservices arriving in physical form.

Pattern Writes Failover Complexity
Active-passive One region only Promote the standby Lowest
Active-active, partitioned Each region owns some users Reroute that slice Moderate
Active-active, shared Anywhere Transparent Conflict resolution

Most teams that think they need active-active need active-passive with a tested failover. The honest question is your RPO and RTO — how much data may be lost, and how long may recovery take — because the answer sets the architecture and the bill.

Seeing what's happening

This isn't a stage — it's the thing that tells you which stage you're in. Add it at stage 1, before you need it.

Every decision on this page depends on measurement. Without it you'll add a cache where the bottleneck was a missing index, or shard a database that was waiting on a lock. The minimum useful set: request rate, error rate, and latency at p50/p95/p99 per endpoint; database query time and slow-query log; cache hit rate; queue depth; and saturation of every pool (threads, connections).

Percentiles, not averages

An average response time of 200ms can hide 5% of users waiting four seconds. The average is the number that looks fine while people churn. Alarm on p99 and you're watching the experience of the users having the worst time — which is where the truth lives.

The whole picture

Everything assembled. Worth seeing once — and worth remembering that nobody built it in this shape from the start.

Estimating

Rough arithmetic that tells you which stage you actually need. Orders of magnitude are the point — precision isn't. 

// Handy approximations
//   a day            ≈ 100,000 seconds   (86,400, rounded)
//   peak traffic     ≈ 2–3× the average
//   1 million × 1KB  ≈ 1 GB

// Worked: a photo-sharing app
//   500K DAU, 2 uploads each        = 1M uploads/day ≈ 12 uploads/s
//   reads are 100× writes           ≈ 1,200 reads/s
//   2MB per photo × 1M              = 2 TB/day of new storage
//   → reads: trivially cacheable, mostly CDN
//   → storage: the actual problem — object storage, not the database

That last line is the value of estimating. The instinct says "1,200 reads per second needs sharding"; the arithmetic says the reads are cacheable and the real constraint is 2TB a day of blobs, which belongs in object storage with a CDN in front. Ten minutes of arithmetic redirects months of work.

Scale Typically needs
< 100 req/s One or two app servers, one database
~1,000 req/s Load balancer, replicas, cache, CDN
~10,000 req/s Plus queues, heavy caching, maybe sharding
100,000+ req/s Sharding, multi-region, purpose-built stores

Ways to get hurt

Scaling before measuring

The most expensive mistake here. Adding a cache when the problem was a missing index leaves you with both the original slowness and a new consistency bug to maintain. Profile first, every time.

Skipping vertical scaling

Doubling the instance size takes ten minutes and adds no failure modes. Distributing a system takes months and adds many. Use the boring option until it genuinely runs out.

Keeping state on app servers

Sessions, uploaded files, in-process caches, scheduled jobs that assume they're the only instance. Each one quietly prevents horizontal scaling, and each surfaces as a bizarre intermittent bug the moment you add the second server.

Caching without an invalidation story

Easy to add, hard to reason about. If you can't state how stale a value may be and what evicts it, you've introduced a correctness bug that'll surface as "the site shows the wrong price".

Sharding too early, or on the wrong key

Sharding is the hardest step to reverse. A poorly chosen shard key means either hotspots or cross-shard queries for everything, and fixing it means migrating every row. Exhaust the reversible options first.

Forgetting the database is still one machine

Ten app servers behind a load balancer all talk to one primary. Scaling the stateless tier is easy and feels like progress while the real ceiling sits untouched behind it.

No tested failover

A replica you've never promoted and a backup you've never restored are both assumptions. Practise them on a normal Tuesday, not during the incident.

The short version

Start on one box. Split the database, add a load balancer and make the app stateless, add replicas, then a cache, then a CDN, then queues — and only then consider sharding and multiple regions. Measure before each step, prefer the reversible option, and remember that most systems never need the second half of this list.
