microservices · and the system design underneath

Inside Microservices

Splitting a system into services doesn't remove complexity — it moves it onto the network, where calls can be slow, fail halfway, or arrive twice. Everything worth knowing about microservices is a technique for living with that move.

The real trade

A monolith calls a method. A microservice makes a network request. That one substitution is the source of every benefit and every problem that follows.

The most dangerous line in that diagram is "can succeed but look failed". The payment went through, the response was lost, and the caller retries. Every service that receives a request over a network must be designed to receive it twice.

When not to

The most common microservices mistake is adopting them. Most systems should start as a well-structured monolith.

Signal Points to
One or two teams Modular monolith
Domain not yet understood Monolith — you'll draw the boundaries wrong
No automated deploys or monitoring Monolith — you can't operate services yet
Many teams blocked on one release train Microservices
One part needs 50× the scale of the rest Extract that part
Parts need different languages or runtimes Microservices
The distributed monolith

The worst outcome: services that must be deployed together, share a database, and call each other synchronously in long chains. You pay every cost of distribution — latency, partial failure, harder debugging — and receive none of the independence. If changing one service routinely requires changing three others in lockstep, this is what you've built.

Conway's law is the useful lens: systems end up mirroring the communication structure of the organisations that build them. Service boundaries that cut across team boundaries fight the organisation forever. Draw them along team lines.

If you have a monolith and genuinely need to split it, the strangler fig pattern is the safe route: route one capability at a time to a new service behind the same entry point, leaving the rest in place, until the old system has nothing left to do.

Drawing boundaries

A good boundary means a service can change without its neighbours noticing. The tool for finding them is Domain-Driven Design's bounded context.

The same word means different things in different parts of a business. To sales, a Customer is a lead with a pipeline stage. To billing, it's a payment method and an invoice history. To shipping, it's an address. Forcing one Customer class to serve all three produces a model nobody can change safely. A bounded context is the region inside which one meaning holds — and that region is a candidate service.

If two services read the same table, neither can change its schema without coordinating with the other — which is exactly the coupling you split them to escape. Each service owns its data outright, and everyone else gets it through the API or through events. It's the rule that makes the rest work.

A common wrong split is by technical layer — a "database service", a "validation service", a "UI service". Every feature then touches every service, so nothing is independent. Split by what the business does, not by how the code is layered.

Sync vs async

Services talk two ways, and the choice decides how failures spread.

Synchronous — REST, gRPC Asynchronous — events, Kafka
Caller waits? Yes No
If callee is down Caller fails too Message waits in the log
Coupling Temporal — both must be up Only to the event format
Consistency Immediate Eventual
Debugging A stack of calls Needs tracing
Good for Queries, user-facing reads Things that happened, fan-out

A useful default: commands and queries that need an answer now go synchronous; events announcing that something already happened go asynchronous. OrderPlaced is an event — billing, shipping and email each react in their own time, and none of them blocks checkout.

REST is the lingua franca and easy to debug. gRPC is faster, strongly typed through Protobuf, and supports streaming, at the cost of tooling friction and being harder to call from a browser. The async side is covered in depth in Inside Kafka.

Gateway and discovery

Clients shouldn't know your service topology, and services shouldn't hard-code each other's addresses.

  • Server-side discovery — a load balancer or a Kubernetes Service resolves the name for you. The default in container platforms, and the one to prefer.
  • Client-side discovery — the caller asks a registry such as Eureka and picks an instance itself. More control, more logic in every client.
  • Backend-for-frontend (BFF) — a separate gateway per client type, so the mobile app gets a lean aggregated payload and the web app gets its own shape.

Cascading failure

The defining failure of microservices: one slow dependency takes down everything that calls it — not by crashing, but by holding every thread hostage while it waits.

Chains also multiply unreliability. Five services at 99.9% availability, called in sequence, give 0.999⁵ ≈ 99.5% — roughly five times the downtime of any single one. Every synchronous hop you add lowers the ceiling of the whole request.

Resilience patterns

Four patterns, each cutting the cascade at a different point. You need all of them, and the order you apply them in matters.

Timeouts — the one you can never skip

Every network call needs one. The default for many HTTP clients is infinite, which is precisely how the cascade above happens. Set the timeout from the dependency's real latency percentiles, not a round number, and remember that a timeout doesn't mean the call failed — only that you stopped waiting.

Retries — with backoff, jitter, and restraint

// ✗ Immediate retries turn a struggling service into a dead one.
//   Every client multiplies its load at the exact moment it's weakest.

// ✓ Exponential backoff with jitter, and a cap
long delay = Math.min(maxDelay, base * (1L << attempt));
long jittered = ThreadLocalRandom.current().nextLong(delay);   // spread clients out

// Only retry what's safe to repeat — and make it safe with a key:
//   POST /payments   Idempotency-Key: 7f3a…
// the server stores the key and returns the original result on a repeat

Without jitter, every client that failed at the same moment retries at the same moment, in synchronised waves — a retry storm. Jitter spreads them out. And retries stack across layers: three layers retrying three times each is 27 attempts on the bottom service.

Circuit breaker — stop calling what's broken

Bulkheads — contain the damage

Named after the watertight compartments in a ship. Give each downstream dependency its own bounded thread pool or semaphore, so a slow bank API can exhaust its pool without touching the pool that serves product search. 

// Resilience4j — stacked in the order they should apply
@CircuitBreaker(name = "bank", fallbackMethod = "queueForLater")
@Retry(name = "bank")
@Bulkhead(name = "bank")
@TimeLimiter(name = "bank")
public CompletableFuture<Receipt> charge(Payment p) { … }

// A fallback should degrade gracefully, not pretend:
//   serve cached data, queue the work, or return a clear "try later"
These are proxy-based annotations

Resilience4j's annotations work through Spring AOP, so they inherit the self-invocation trap from Inside Spring: call this.charge() from inside the same bean and no breaker, retry or timeout applies. The annotation is present and does nothing.

CAP and consistency

Once data lives in more than one place, you have to choose what happens when those places can't talk to each other.

CAP says that during a network partition a distributed system must choose between consistency (every read sees the latest write, or errors) and availability (every request gets a response, possibly stale). Partitions aren't optional in real networks, so the practical choice is C or A when they happen.

Choose consistency (CP) Choose availability (AP)
During a partition Refuse some requests Serve possibly stale data
Suits Balances, inventory, bookings Feeds, likes, recommendations
Examples ZooKeeper, etcd, most SQL setups Cassandra, DynamoDB (default)

PACELC finishes the thought: else, when there's no partition, you're still trading latency against consistency — because waiting for replicas to confirm costs time. That's the trade you make on every normal request, which is why it matters more day to day than CAP does.

Eventual consistency is a product decision

It's often fine, and sometimes it isn't. A like count being two seconds stale harms nobody. An account balance showing money that's already been spent harms someone badly. Decide per piece of data with the people who own the product, not globally as an architecture choice.

Sagas

There is no transaction spanning services. A saga replaces it with a sequence of local transactions, each with a compensating action that undoes it if a later step fails.

Choreography Orchestration
How Each service reacts to events A coordinator tells each service what to do
Central logic None — it's spread out In one place
Easy to follow? Hard past 3–4 steps Yes — read the orchestrator
Coupling Low Services coupled to the orchestrator
Good for Short, simple flows Long flows, complex compensation

Two-phase commit exists and can technically span services, but it blocks every participant while the coordinator decides, and a coordinator failure can leave them locked indefinitely. That's why sagas, not 2PC, are the standard answer. For orchestration, workflow engines such as Temporal or Camunda handle the state machine, retries and timeouts for you.

The outbox

Saving to your database and publishing an event are two separate systems. Doing both correctly is harder than it looks — this is the dual-write problem.

Reversing the order doesn't help: publish first and a failed save leaves an event describing an order that doesn't exist. The outbox works because it turns two systems into one — the database — and lets a separate process do the second write reliably. Change data capture tools like Debezium can read the outbox straight from the database's transaction log instead of polling.

Scaling

The system design fundamentals that decide whether any of this survives real traffic.

Technique What it does The catch
Vertical scaling Bigger machine A ceiling, and a single point of failure
Horizontal scaling More machines behind a load balancer Only works if the service is stateless
Read replicas Copies of the DB serving reads Replication lag — reads can be stale
Sharding Split data across databases by key Cross-shard queries and rebalancing hurt
Caching Keep hot data in memory Invalidation
Async processing Queue work for later Eventual consistency
CDN Serve static content from the edge Purging on change

Stateless is the precondition

A load balancer can send any request to any instance only if no instance remembers anything between requests. Session data in instance memory breaks that — users get logged out when routed elsewhere. Move state to a shared store (Redis, the database) or into the request itself (a signed token), and instances become interchangeable.

Sharding and consistent hashing

Sharding by hash(key) % N works until N changes — then almost every key moves to a different shard. Consistent hashing places shards and keys on a ring so adding a shard moves only about 1/N of the keys. It's the same insight as HashMap's resize from Inside Java Maps, taken across machines. Pick the shard key carefully: a bad one sends all traffic to one hot shard, and changing it later means migrating everything.

Rate limiting

Protects a service from being overwhelmed, whether by a buggy client or a traffic spike. The token bucket is the usual algorithm: tokens refill at a steady rate up to a cap, each request spends one, and an empty bucket means reject. The cap lets short bursts through while the refill rate enforces the long-run average.

Caching

The cheapest performance win in system design, and the source of its most famous hard problem.

The thundering herd

A popular key expires and a thousand requests miss at once — all of them hit the database simultaneously, which is exactly the load the cache was protecting it from. Defences: jitter the TTLs so keys don't expire together, let only one request rebuild a key while others wait (a lock or "single flight"), or refresh hot keys before they expire.

Every cache needs a stated answer to "how stale can this be?", and a TTL is that answer made explicit. If nobody on the team can say what the acceptable staleness is for a piece of data, it isn't ready to be cached.

Observability

In a monolith a stack trace tells you what happened. In microservices the story is scattered across a dozen processes' logs — unless you deliberately stitch it back together.

Logs

What happened, in detail. Structured JSON, one line per event, always carrying a trace id so lines from different services can be joined.

Metrics

How much and how fast, aggregated over time. Cheap to store. Tells you that something's wrong.

Traces

One request's path through every service, with timings per hop. Tells you where it's wrong.

The glue is context propagation: the gateway assigns a trace id, and every service passes it along in a header (the W3C traceparent standard) and logs it. OpenTelemetry is the vendor-neutral standard for all three signals. In Spring Boot 3, Micrometer Tracing wires this up, including propagation across HTTP clients and Kafka.

The four golden signals — watch these per service

  • Latency — at percentiles. The average hides the users having a terrible time; watch p99.
  • Traffic — requests per second.
  • Errors — the rate of failed requests, including slow ones you'd count as failures.
  • Saturation — how full the service is: thread pools, connection pools, queue depth. This is the one that predicts the cascade.

Deploying

Independent deployment is the whole reason for microservices. That only holds if every release is safe to ship on its own.

Strategy How Rollback
Rolling Replace instances a few at a time Slow — roll forward again
Blue-green Full new copy, switch traffic at once Instant — switch back
Canary Send a small slice of traffic to the new version first Stop the canary
Feature flags Ship the code dark, turn it on separately Flip the flag
Backward compatibility is what makes independent deploys possible

During any rollout, old and new versions run side by side and talk to each other. So every API change and every event schema change must be compatible in both directions for at least one release: add fields, never rename or remove them in the same step. Changing a contract is always two deploys — expand, then contract once nothing uses the old shape.

Designing a system

A repeatable order of work for any "design X" problem — in an interview or at a whiteboard with your team. The order matters more than any single answer.

  1. Clarify requirementsFunctional: what must it do? Non-functional: scale, latency, availability, consistency. Ask — don't assume a billion users.
  2. EstimateRequests per second, read/write ratio, storage per year. Rough orders of magnitude decide the whole shape of the design.
  3. Define the APIThe handful of calls clients make. This pins down what the system actually is.
  4. Model the dataEntities, access patterns, SQL or NoSQL. Choose the store from how the data is read, not from habit.
  5. Draw the high-level designClients, load balancer, services, stores, caches, queues. Keep it simple enough to explain in two minutes.
  6. Deep-dive the hard partsThe bottleneck, the consistency boundary, the hot key. This is where the design is really tested.
  7. Name the trade-offs and failure modesWhat breaks first, what happens when a dependency is down, and what you'd change at ten times the scale.

// 200M / 86,400 s ≈ 2,300 req/s average
// peak ≈ 2–3× average           ≈ 5,000–7,000 req/s
// 1KB per write × 20M writes/day ≈ 20GB/day ≈ 7TB/year

Numbers to know

Orders of magnitude, not exact values — they vary by hardware. What matters is the ratio between them, which tells you where time goes.

Operation Roughly What it means
Main memory reference 100 ns The baseline
Read 1 MB sequentially from memory ~0.25 ms Memory is fast for bulk
Round trip within a datacenter ~0.5 ms Every service hop costs this
SSD random read ~0.1 ms Much faster than spinning disk
Disk seek ~10 ms Why databases avoid random I/O
Round trip across continents ~150 ms Why CDNs and regions exist
Availability Downtime per year Per month
99% ~3.65 days ~7.3 hours
99.9% ~8.8 hours ~44 minutes
99.99% ~53 minutes ~4.4 minutes
99.999% ~5.3 minutes ~26 seconds

Each extra nine is ten times harder and usually costs far more than ten times the money. It's also why the 0.999⁵ calculation from the cascade section matters: a chain of five three-nines services can't be a three-nines system.

Container platforms now handle much of what used to need a library: Kubernetes provides discovery, load balancing and config, and a service mesh such as Istio can add retries, timeouts and mTLS without changing application code. Ways to get hurt

Starting with microservices

You'll draw boundaries before understanding the domain, and moving a boundary later means moving data between databases. Start with a modular monolith with clean internal boundaries, and extract services once a boundary has proven itself.

Sharing a database between services

The fastest way to a distributed monolith. It looks like a shortcut and permanently couples the schemas of everything that touches the table.

A network call with no timeout

Many clients default to waiting forever. One slow dependency then holds every thread in every caller — the cascade. There is no such thing as a call that doesn't need a timeout.

Retrying without backoff, jitter, or idempotency

Instant retries attack a struggling service at its weakest moment, synchronised retries arrive in waves, and retrying a non-idempotent call charges the customer twice. Get all three right or don't retry.

Long synchronous call chains

Latency adds up and availability multiplies down with every hop. If a request routinely touches six services in sequence, the design needs events, caching or a reshaped boundary — not a faster network.

Writing to the database and publishing separately

Any crash between the two leaves them out of step, silently. Use the outbox.

No trace id

Without one, investigating a failed request means grepping a dozen services' logs by timestamp and guessing. Add propagation on day one; retrofitting it is miserable.

Breaking a contract in one deploy

Renaming a field breaks every consumer still running the old version, and during a rollout that's guaranteed to include some. Expand first, migrate consumers, contract later.

The short version

Microservices trade method calls for network calls, and every technique here exists to handle what that costs. Split along team and business lines, give each service its own data, put a timeout on every call, prefer events to long chains, replace transactions with sagas and the outbox, make every handler idempotent, and trace everything. And if one team can own the whole system, you probably don't need any of it yet.
